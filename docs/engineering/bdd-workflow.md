# 행동 중심 개발 흐름

기대 행동을 짧게 합의하고 구현·검증까지 이어간다. 승인 경계는 [AGENTS.md](../../AGENTS.md), 검사 선택과 증거 재사용은 [testing.md](testing.md)를 따른다.

## 작업 시작

- 읽기·조사·리뷰에는 이슈를 요구하지 않는다. 저장소를 수정하는 작업은 이슈와 그 범위에서 진행한다.
- 이슈가 없으면 관련 코드를 확인하고 범위·접근법·위험·검증을 간단히 제시한 뒤 이슈 생성과 구현 진행을 함께 확인한다. 사용자가 이미 둘 다 승인했다면 바로 이슈를 만들고 진행한다.
- 이슈 생성만 요청했다면 구현까지 승인한 것으로 확대하지 않는다. 승인한 작업의 평범한 구현 선택·테스트·수정에는 재승인을 요구하지 않는다.
- 기능은 성공·거절·경계 행동, 버그는 재현과 기대 결과, 문서·하네스는 관찰 가능한 완료 기준으로 정의한다. Given/When/Then은 유용한 표현 방식이며 필수 서식은 아니다.
- 필요한 행동이 대화나 이슈에 이미 명확하면 시나리오를 정리하고 계속한다. 결과를 바꾸는 모호함만 질문한다.

## 구현과 확인

- 중요한 업무 규칙·버그는 red/green TDD: 기대한 이유로 실패하는 테스트를 확인하고 최소 구현한다. 일반 기능도 변경 행동을 검증하는 테스트를 남긴다.
- 관련 테스트를 빠르게 반복한다. 테스트 기대값은 요구사항에 근거하고, 구현에 맞추기 위한 삭제·무력화는 금지한다.
- 이슈 범위에서 구현, 관련 검사, 필요한 실제 동작 확인, 발견한 결함 수정을 연속 수행한다.
- 단순 변경에는 관련 검사와 diff 리뷰를 적용한다. 인증·권한·DB·트랜잭션·동시성 등 위험이 있는 변경에는 통합 검증과 전문 리뷰를 추가한다.

## 리뷰 선택

모든 변경에서 diff와 영향받는 호출부를 확인한다. 파일 수만으로 전문 리뷰를 요구하지 않는다.

| 변경 | 추가 리뷰 |
| --- | --- |
| 새 도메인 구조 | `domain-reviewer` |
| 모듈·계층 경계, JPA 쿼리·저장 방식, 트랜잭션·동시성, 넓은 공개 계약 변경 | `java-reviewer` |
| OAuth2, JWT, 인증·인가, Security 필터·인터셉터, 인증·결제 입력 처리 변경 | `security-reviewer` |
| 원인이 명확하지 않거나 반복되는 Gradle 빌드 실패 | `java-build-resolver` |

- 리뷰어는 요청한 범위와 관련 기준을 읽고 발견 사항을 보고한다. 읽기 전용 리뷰어는 수정하지 않는다.
- 같은 변경을 여러 단계에서 같은 리뷰어에게 반복 제출하지 않는다. 수정한 부분과 영향 범위를 재검토한다.
- CRITICAL/HIGH 발견은 수정·재검토 후 완료한다. 교차 모델 리뷰는 사용자 요청이나 해결되지 않은 고위험 쟁점이 있을 때 사용한다.

## 완료

변경 결과, 실행한 검증과 증거, 남은 제한을 간결하게 보고한다.
커밋·푸시·PR 권한이 없다면 검증된 결과를 제시한 뒤 한 번 확인한다.
